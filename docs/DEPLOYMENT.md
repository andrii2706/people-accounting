# Розгортання: Firebase App Hosting + Cloud Run + Cloud SQL

> Це одноразове налаштування інфраструктури. Щоденний процес випуску змін, правила міграцій і відкат —
> у [DEPLOYMENT-PROCESS.md](DEPLOYMENT-PROCESS.md).

```
 Браузер ──HTTPS──▶ Firebase App Hosting (Angular SSR, Express)          us-east4
                      │  /api/*  → проксі + ID-токен сервісного акаунта
                      ▼
                    Cloud Run «military-registry-api» (NestJS)        ← без публічного доступу (IAM)
                      │  Cloud SQL connector (IAM + TLS)      │  Secret Manager
                      ▼                                       ▼
                    Cloud SQL PostgreSQL 16              Cloud Storage (підписані документи,
                    (бекапи, PITR, шифрування)           retention / write-once)
```

* **Фронтенд** — Firebase App Hosting (керований Cloud Run для SSR-фреймворків). Збирається з гілки `main`
  автоматично, конфігурація — `frontend/apphosting.yaml`, `firebase.json`.
* **API** — окремий Cloud Run, викликати його може **лише** сервісний акаунт App Hosting
  (`roles/run.invoker`). Браузер не має прямого доступу до API: усі запити йдуть через `/api` на тому ж домені.
* **БД** — Cloud SQL без authorized networks: підключення тільки через Cloud SQL connector.
* **Секрети** — Secret Manager (регіональні, лише `us-east4`), у коді та в GitHub їх немає.
* **CI/CD** — GitHub Actions з Workload Identity Federation (без JSON-ключів), обов'язкове підтвердження
  деплою через GitHub Environment `production`.

> Чому не класичний Firebase Hosting + Functions: Hosting пропускає до бекенду лише cookie `__session`,
> а API в Functions не дає приватності на рівні IAM так просто, як Cloud Run. App Hosting — офіційний шлях
> для Angular SSR у Firebase.

Регіон `us-east4` (Північна Вірджинія, США) — App Hosting, Cloud Run і Cloud SQL в одному регіоні, щоб SSR → API → БД
не ходили між регіонами. Інший регіон задається змінною `REGION` для `infra/bootstrap.sh` і змінною GitHub `GCP_REGION`.
Транскордонну передачу персональних даних погодьте з відповідальним за захист даних у компанії
(ЗУ «Про захист персональних даних», ст. 29).

## 1. Передумови

* Проєкт Google Cloud з тарифом **Blaze**, ви — Owner.
* `gcloud` (≥ 500), `firebase-tools` (≥ 14), `openssl`.
* Репозиторій на GitHub (код з кореня цього архіву).

## 2. Інфраструктура — один скрипт

```bash
PROJECT_ID=my-company-military \
GITHUB_REPO=my-org/military-registry \
APP_DOMAIN=oblik.company.ua \
./infra/bootstrap.sh
```

Скрипт ідемпотентний і створює:

| Ресурс | Налаштування безпеки |
|---|---|
| Cloud SQL `military-registry-db` | `ENCRYPTED_ONLY` TLS, без authorized networks, бекапи 30 днів, PITR 7 днів, deletion protection |
| Секрети `DATABASE_URL`, `JWT_SECRET`, `DATA_ENCRYPTION_KEY`, `BLIND_INDEX_KEY`, `ADMIN_PASSWORD` | генеруються випадково, регіональна реплікація, доступ лише в API-акаунта |
| Бакет `<project>-mr-signed-docs` | без публічного доступу, uniform access, retention 5 років |
| SA `mr-api` (runtime API) | `cloudsql.client`, читання конкретних секретів, у бакеті — лише створення й читання (без видалення) |
| SA `mr-github-deployer` | `run.admin`, запис в Artifact Registry, `actAs` лише на `mr-api` |
| Workload Identity Federation | токен лише для цього репозиторію, гілки `main` і environment `production` |

Наприкінці скрипт надрукує тимчасовий пароль адміністратора (його попросять змінити при першому вході)
і значення змінних для GitHub.

## 3. GitHub

1. **Settings → Environments → New environment `production`**: увімкніть *Required reviewers*
   і *Deployment branches: main*.
2. **Settings → Secrets and variables → Actions → Variables** — значення з виводу скрипта:
   `GCP_PROJECT_ID`, `GCP_REGION`, `GCP_WIF_PROVIDER`, `GCP_DEPLOY_SA`, `GCP_API_SA`, `GCP_SQL_INSTANCE`,
   `GCP_BUCKET`, `GCP_WEB_SA`, `APP_ORIGIN`, `ADMIN_EMAIL`.
   Необов'язково: `SIGN_WIDGET_SCRIPT_URL`, `SIGN_WIDGET_FRAME_URL` (див. [KEP.md](KEP.md)).
3. **Settings → Branches**: захист `main` (PR + зелений CI).

Workflows:

| Файл | Коли | Що робить |
|---|---|---|
| `.github/workflows/ci.yml` | PR і push | lint, тести, збірка, міграції up→down→up на чистій БД, `npm audit`, збірка Docker |
| `.github/workflows/deploy-api.yml` | push у `main` (зміни в `backend/`) або вручну | образ → Artifact Registry → **міграції (Cloud Run Job)** → деплой API (`--no-allow-unauthenticated`) → `run.invoker` для App Hosting → перевірка, що немає `allUsers` |
| `.github/dependabot.yml` | щотижня | оновлення залежностей |

## 4. Перший деплой API

Запустіть **Actions → Deploy API → Run workflow**. Після підтвердження у `production` у логах буде URL API
(`https://military-registry-api-….us-east4.run.app`). Відкрити його в браузері не вийде — 403, так і має бути.

## 5. Фронтенд — Firebase App Hosting

```bash
firebase projects:addfirebase $PROJECT_ID          # якщо проєкт ще не Firebase
firebase apphosting:backends:create \
  --project $PROJECT_ID --location us-east4 --backend people-accounting
#   → підключіть GitHub-репозиторій, root directory: frontend, live branch: main
```

> ⚠️ **Root directory = `frontend`**, регіон — **us-east4**. Якщо вказати корінь репозиторію (`/`),
> збірка падає з `package.json not found` / `No buildpack groups passed detection`. Регіон бекенда
> App Hosting змінити не можна — лише видалити й створити заново. Бекенд (`backend/`) в App Hosting
> не додається — він розгортається в Cloud Run (крок 4).

`frontend/apphosting.yaml` заповнювати не треба: адресу API (`https://military-registry-api-<номер проєкту>.<регіон>.run.app`)
SSR-сервер визначає сам. `API_INTERNAL_URL` задавайте лише якщо API в іншому регіоні або під іншою назвою. За потреби:

* `NG_ALLOWED_HOSTS` не потрібен — App Hosting задає його сам; розкоментуйте лише для власного домену
  (і перелічіть там також `people-accounting--<project>.us-east4.hosted.app`);
* за потреби `ALLOWED_CLIENT_CIDRS` — доступ лише з офісу/VPN.

Push у `main` → App Hosting збере й розгорне SSR. Власний домен: Firebase Console → App Hosting →
*Custom domains* (TLS-сертифікат видається автоматично), потім додайте домен у `NG_ALLOWED_HOSTS`
і в змінну GitHub `APP_ORIGIN`.

## 6. Після першого входу

1. Увійдіть як `ADMIN_EMAIL` з тимчасовим паролем → система попросить змінити пароль.
2. *Юридичні особи*: міграція `LegalEntities` перенесла старі реквізити, поточного керівника й відповідального
   в першу юрособу — перевірте їх (код ЄДРПОУ `00000000` означає, що код не був заповнений). Нову юрособу можна
   заповнити кнопкою «Підтягнути з ЄДР» (див. § 6д) і перевірити посиланням «Перевірити в YouControl».
3. *Довідник ТЦК* — окремий пункт меню. *Налаштування* — це юридичні особи (реквізити, керівник, відповідальний,
   квота бронювання, адреси нагадувань), *Користувачі* і *Загальні параметри* (строки попереджень, строк мобілізації).
4. Доступ керівнику й відповідальному — у картці юрособи (§ 6д); іншим — *Налаштування → Користувачі*.

## 6а. Пошта, щоденні нагадування й укази про мобілізацію

Щодня о 07:00 (Київ) Cloud Scheduler запускає Cloud Run Job `military-registry-daily`
(створюється кроком «Deploy API»). Він:

* перевіряє укази Президента про продовження мобілізації на zakon.rada.gov.ua (`DECREE_SOURCE_URL`)
  і оновлює «Строк мобілізації» (див. *Налаштування → Загальні параметри*; там же є кнопка «Перевірити укази зараз»
  і ручне введення на випадок недоступності сайту);
* надсилає листи: відстрочка закінчується за ≤ 5 днів (зокрема «до завершення мобілізації»),
  бронювання закінчується, мобілізація закінчується за 14 днів. Один лист на день, без повторів.

Листи отримують активні користувачі з увімкненим «Отримувати листи» (Профіль; адмін може
вимкнути в *Користувачі*) і додаткові адреси юрособи, до якої належить працівник (*Налаштування → юрособа → «Нагадування на пошту»*).
Користувачам також приходять листи про створення облікового запису, зміну ролі, скидання пароля
та зміну керівника підприємства.

Налаштування SMTP (один раз):

```bash
# 1) секрет SMTP_URL (Gmail: App Password, smtps://…:465; або SMTP поштового сервісу компанії)
SMTP_URL='smtps://hr%40company.ua:APP_PASSWORD@smtp.gmail.com:465' \
PROJECT_ID=accounting-project-1aecf GITHUB_REPO=andrii2706/people-accounting \
  ./infra/bootstrap.sh            # повторний запуск безпечний: додасть Scheduler-ролі і секрет
# 2) змінна GitHub (environment production): MAIL_FROM = Військовий облік <hr@company.ua>
# 3) Actions → Deploy API → Run workflow
```

Перевірка: *Налаштування → Пошта і нагадування → Надіслати тестовий лист* (лист прийде на вашу адресу).

> Листи містять ПІБ працівників — використовуйте лише `smtps://` (TLS) і корпоративну скриньку.

## 6г. Заборгованість за користування (постачальник)

Після кожного входу користувач бачить блок: «Ласкаво просимо» або «Є заборгованість» (сума, дата, контакт
для оплати — якщо задані). Поки є заборгованість, **кожен користувач може увійти один раз**; наступний
вхід блокується з повідомленням про заборгованість, доки її не знімуть. Нова заборгованість знову дає
кожному один вхід. Адміністратор клієнта змінити це не може.

Керує заборгованістю постачальник — двома способами:

* **сторінка `/vendor`** під обліковим записом постачальника (бачить лише цю сторінку, без персональних даних;
  у списку користувачів клієнта його немає);
* **команда** — локально `cd backend && npm run billing -- …`, у продакшні тим самим образом через
  Cloud Run Job щоденної задачі з іншими аргументами:

```bash
# стан
gcloud run jobs execute military-registry-daily --region us-east4 --wait --args=dist/jobs/billing.js
# встановити заборгованість (сума, дата й контакт — необов'язкові)
gcloud run jobs execute military-registry-daily --region us-east4 --wait \
  --args=dist/jobs/billing.js,--debt,--amount,1500,--since,2026-11-01,--contact,"+380 67 000 00 00"
# зняти
gcloud run jobs execute military-registry-daily --region us-east4 --wait --args=dist/jobs/billing.js,--clear
# створити обліковий запис постачальника (пароль згенерується і з'явиться один раз у логах виконання)
gcloud run jobs execute military-registry-daily --region us-east4 --wait \
  --args=dist/jobs/billing.js,--create-vendor,vendor@company.ua,"Постачальник"
```

Результат — у логах виконання: *Cloud Run → Jobs → military-registry-daily → Executions → Logs*.
Локально пароль можна задати четвертим аргументом: `npm run billing -- --create-vendor <email> "<ім'я>" "<пароль>"`.

## 6д. Юридичні особи, пошук у ЄДР, старі повідомлення й витяги

**Юридичні особи.** Кожен працівник належить одній юрособі. Списки, витяги, відомість, повідомлення ТЦК і наклейки
формуються від її імені — з її реквізитами, керівником (підпис) і відповідальним за військовий облік (виконавець).
Керівник і відповідальний — лише поточні відомості: якщо людина змінилась, її просто переписують у картці юрособи.
Поки юрособа одна, вибирати її ніде не треба; коли їх кілька — у картці працівника, імпорті, списках, відомості
й витягах з’являється вибір.

**Ролі й розділення даних.** Кожен обліковий запис, крім головного адміністратора, належить одній юрособі
(`users.legalEntityId`) і бачить лише її: працівників, листи й повідомлення ТЦК, списки, відомість, витяги, огляд,
сповіщення, користувачів. Запис іншої юрособи сервер відповідає як неіснуючий (404), тож чужі id не перебрати.

| Роль | Що може |
|---|---|
| `ADMIN` — головний адміністратор | усі юрособи й дані, усі користувачі (і юрособа кожного), загальні параметри, довідник ТЦК, видалення юрособ |
| `ENTITY_ADMIN` — адміністратор юрособи | облік своєї юрособи, її реквізити, квота, нагадування, доступи керівника й відповідального, журнал, користувачі-кадровики й директори своєї юрособи |
| `DIRECTOR` — директор | те саме, що адмін юрособи; поки юрособи немає — додає **свою** (одну) і стає її керівником |
| `HR` — відповідальний за військовий облік | облік своєї юрособи: працівники, повідомлення, листи, звіти |

Адміністратора юрособи призначає лише головний адміністратор. Директора без юрособи створює головний адміністратор
(*Користувачі*, юрособу не обирати) — після входу директор одразу потрапляє на «Нова юридична особа». Обліковий запис
кадровика / адміністратора юрособи без юрособи бачить лише сторінку «зверніться до головного адміністратора».
Вихідні листи нумеруються окремо в кожній юрособі. Довідник ТЦК спільний, тому змінює його лише головний
адміністратор. Нагадування на пошту отримують користувачі юрособи працівника (і головні адміністратори).
Міграція `EntityRoles1793320000000` прив’язує наявні записи керівника й відповідального до їхніх юросіб, а коли
юрособа одна — і всіх інших; решту (якщо такі є) головний адміністратор прив’язує в *Користувачах*.

**Доступ керівника й відповідального** (головний адміністратор, адміністратор або директор цієї юрособи). У картці
юрособи → «Доступ до системи»: email (це логін) і роль (відповідальний / директор; адміністратора юрособи — лише
головний адміністратор; керівнику за замовчуванням — «Директор») → система створює обліковий запис і надсилає людині лист з логіном і тимчасовим
паролем з окремої скриньки для доступів (див. нижче); адміністратору пароль теж показується один раз — на випадок,
якщо лист не дійде. Тимчасовий пароль діє `TEMPORARY_PASSWORD_HOURS` (72 год.) і до першої зміни; прострочений
не приймається — адміністратор скидає пароль (*Користувачі → «Скинути пароль»*, теж з листом).
Під час першого входу людина встановлює власний пароль. Якщо обліковий запис з таким email уже є —
його просто прив’язують (пароль не змінюється). «Змінити керівника / відповідального» замінює ПІБ, посаду,
телефон і за потреби скасовує доступ попереднього та одразу дає доступ новому. «Скасувати доступ» вимикає
обліковий запис (сеанси завершуються одразу); запис не видаляється, щоб лишився журнал дій. Власний доступ
адміністратор скасувати не може.

**Скринька для листів з паролем.** Окрема адреса (напр. `access@company.ua`), щоб листи з доступом не губилися
серед нагадувань. Без неї листи йдуть з основної `SMTP_URL` / `MAIL_FROM`; без жодної — не надсилаються (пароль
лише на екрані адміністратора).

```bash
# секрет зі скринькою (Gmail: App Password) і доступ до нього для сервісного акаунта API
printf '%s' 'smtps://access%40company.ua:APP_PASSWORD@smtp.gmail.com:465' | \
  gcloud secrets create ACCESS_SMTP_URL --data-file=- --project accounting-project-1aecf
gcloud secrets add-iam-policy-binding ACCESS_SMTP_URL --project accounting-project-1aecf \
  --member "serviceAccount:$(gh variable get GCP_API_SA)" --role roles/secretmanager.secretAccessor
# відправник — змінна GitHub
gh variable set ACCESS_MAIL_FROM --body 'Військовий облік <access@company.ua>'
```
(Або разом з першим налаштуванням: `ACCESS_SMTP_URL=… ./infra/bootstrap.sh`.)
Наступний деплой API підхопить секрет автоматично (крок перевіряє, чи він існує).

**Строк дії пароля й листи про зміну.** Паролі кадровиків (`HR`) і директорів діють півроку
(`PASSWORD_MAX_AGE_DAYS=180`, ролі — `PASSWORD_EXPIRY_ROLES`). Два листи з тієї ж скриньки для доступів:
1. *Нагадування з можливістю зміни* — щоденна задача за місяць (`PASSWORD_REMINDER_DAYS`) до кінця строку
   надсилає лист з датою й кнопкою «Змінити пароль» (посилання діє тиждень, одноразове). Один лист на кожен строк.
2. *Лист на зміну пароля* — адміністратор: *Користувачі → «Лист на зміну пароля»* (будь-якому користувачу).
   Посилання діє `PASSWORD_LINK_HOURS` (72 год.); до зміни пароля користувач бачить лише сторінку пароля.

Після закінчення строку вхід відкриває лише зміну пароля. Посилання з листів ведуть на `/reset-password`,
працюють без входу й лише один раз; після зміни всі сеанси користувача завершуються. Для наявних облікових
записів відлік півроку почався з міграції `PasswordResetTokens`.

**Роль «Директор»** бачить усе (працівники, списки, витяги, листи, звіти) і підписує документи КЕП, але нічого
не змінює: сервер відхиляє будь-які зміни, крім підпису, власного пароля, сповіщень, позначок «прочитано»
і додавання нової юрособи (редагувати юрособу й видавати доступи може лише адміністратор).

**Квота бронювання й нагадування** — теж у юрособі. Квота вводиться у відсотках: місць = відсоток ×
працюючі військовозобов’язані чоловіки цієї юрособи (призовники, резервісти, жінки й заброньовані іншим
підприємством не рахуються), округлення вниз; вільно = місць − заброньовані самою юрособою. Міграція
`QuotaPercent1793300000000` очищає старі квоти (там було число місць) — їх треба ввести знову у відсотках.
Листи про кінець відстрочки/бронювання отримують користувачі з увімкненими сповіщеннями плюс додаткові
адреси саме тієї юрособи, до якої належить працівник.

**Пошук у ЄДР** (`GET /api/legal-entities/lookup?edrpou=…`, головний адміністратор і директор) — безкоштовне джерело
`COMPANY_REGISTRY_URL` (за замовчуванням `https://adm.tools/action/gov/api/?egrpou={code}`). Сервер бере назву,
скорочену назву, адресу (і з неї індекс) та керівника («ПЕТРЕНКО ІВАН ІВАНОВИЧ» → «Іван ПЕТРЕНКО»), форму
заповнює користувач — нічого не зберігається без «Зберегти». Перевірити відповідь джерела:

```bash
curl -s 'https://adm.tools/action/gov/api/?egrpou=00032129' | head -c 600
```

Якщо формат інший або сервіс недоступний — кнопка покаже «Реєстр не відповідає…», а `COMPANY_REGISTRY_URL`
можна замінити на інше джерело з тими самими полями (`name`, `name_short`, `address`, `director`) або вимкнути
(порожнє значення). Cloud Run має мати вихід в інтернет до цього хоста.

**Старі повідомлення ТЦК** — картка працівника → «Повідомлення до ТЦК» → «Додати старе повідомлення»: номер і дата —
як на папері, лист одразу «надіслано», документа немає; позначені зміни з черги вважаються повідомленими.
Помилково внесене можна видалити (зміни повертаються в чергу).

**Виписки для звірок** — *Звітність → Виписки з списків персонального обліку для звірок*: по кожному ТЦК вих. № і дата
останньої зареєстрованої виписки та кількість офіцерів, військовозобов’язаних
(рядовий, сержантський, старшинський склад), жінок і призовників; витяг .docx («ВИТЯГ ІЗ СПИСКІВ») лише про
осіб, які перебувають на обліку в цьому ТЦК, або реєстрація листа з вихідним номером.

**Наклейки на конверти** — *Налаштування → юрособа → «Наклейки на конверти»* (адміністратор юрособи, директор,
головний адміністратор). Налаштування зберігаються в юрособі (`legal_entities.labelSettings`, міграція
`LabelSettings1793330000000`; без них — як раніше: Times New Roman, одна наклейка на ширину A4). Зміни пишуться в
журнал юрособи. Друк: *Вихідні листи* → позначити листи → «Друкувати наклейки» (сторінка без меню, діалог друку
відкривається сам; у ньому — масштаб 100 %, поля «немає») або «.docx». Листи кількох юросіб друкуються кожна зі
своїми налаштуваннями.

**Телефони** зберігаються як `+<код країни><цифри>` (`+380671234567`); у формі країна вибирається окремо.
Міграція привела наявні номери до цього вигляду.

## 7. Експлуатація

| Задача | Як |
|---|---|
| Оновлення | merge у `main` → CI → Deploy API (з підтвердженням) + App Hosting rollout |
| Відкат API | Cloud Run → Revisions → *Manage traffic* на попередню ревізію (міграції пишіть зворотно сумісними) |
| Відкат фронтенду | Firebase Console → App Hosting → Rollouts → *Roll back* |
| Відновлення БД | Cloud SQL → Backups / Point-in-time recovery (у нову інстанцію, потім перемкнути `DATABASE_URL`) |
| Ротація `JWT_SECRET` | нова версія секрету → новий деплой API → усі сесії завершаться |
| Ротація ключа шифрування | не простою заміною: потрібна міграція перешифрування (стара + нова версія ключа) |
| Журнали | Cloud Logging; журнал дій користувачів — таблиця `audit_log` (вхід, перегляд картки, експорт, підпис) |

### Вартість (орієнтовно)
Cloud SQL `db-custom-1-3840` — основна стаття (~50–60 $/міс). Cloud Run і App Hosting з `minInstances: 0`
для одного відділу кадрів — у межах безкоштовних квот або кілька доларів. Для економії на тестовому
середовищі можна взяти `SQL_TIER=db-f1-micro` (без SLA).

```bash
docker compose up --build        # http://localhost:4000
```
